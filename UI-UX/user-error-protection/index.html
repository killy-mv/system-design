User Error Protection: Bad vs Good

Four interactive examples of designs that turn a small human slip into a big problem, and how layered protection (prevent → detect → confirm → recover → limit damage) fixes them. Every “bad” design here is modeled on a real kind of incident.

Notes: User Error Protection README.

Examples: 1. Bulk delete 2. Money transfer 3. Lost update 4. Ops console

1. The cleanup tool that deletes everything after one typo

Task: delete files older than 30 days. Try it: clear the number (or type 3O with the letter O, or 3 instead of 30) and run the cleanup on both sides.

✗ BAD

Folder “Shared drive / Projects”

Delete selected files?

✓ GOOD

Folder “Shared drive / Projects”

What's wrong

  • parseInt(value) || 0: an empty box becomes 0 (“older than 0 days” = every file), and 3O silently becomes 3.
  • No preview: you never see how many or which files will go.
  • Generic dialog, “Delete selected files?” with OK pre-focused, so pressing Enter deletes. Habituation does the rest.
  • Permanent delete: no trash, no undo. Starred files deleted too.

How it's fixed

  • Strict input parsing with a clear message: invalid input does nothing.
  • Live preview (a dry run): count, size, starred/shared items, examples, and a loud warning when it's every file.
  • Friction scales with impact: the button names the count; more than 100 files requires typing the number.
  • Safe default: starred files skipped.
  • Soft delete: files go to Trash (30-day retention) with an Undo toast.
Principles: Prevent: strict parsing Detect: preview / dry run Confirm: type-to-confirm Recover: soft delete + undo Safe defaults

What's wrong

  • No check-digit validation: a mistyped account number goes to the bank as-is.
  • The payee name is never compared with the account holder. Swapped digits that happen to form another valid account send money to a stranger, and scammers exploit exactly this.
  • No warning for unusual amounts: $8,000 instead of $800 goes straight through.
  • No review step, a vague “Submit” button, and the money is gone instantly. The success message doesn't even say who received it.

How it's fixed

  • Check digit (Luhn) validated as you type: catches every single-digit typo.
  • Payee name verification (like the UK's Confirmation of Payee and the EU's Verification of Payee): match, close match with a suggestion, or no match with a masked name.
  • Soft warning for amounts far above your usual for this payee, and for new accounts.
  • Review screen showing the effect (amount in figures and words, recipient name, masked account), and a button that names the action.
  • 10-second cancel window (delayed execution) before the money actually leaves.
Principles: Detect: check digits Detect: name verification Soft validation Review step shows the effect Recover: delayed execution

3. Two people edit the same product: whose change survives?

Try it in both panels: (1) Bob changes the price to 120 and saves. (2) Alice, whose screen still shows the old data, changes the description and saves. Then try both of them changing the price.

✗ BAD

// requests

✓ GOOD

What's wrong

  • “Last write wins”: Alice's save sends the whole form, including the old price, and silently overwrites Bob's change.
  • Nobody is told. Bob thinks the price is 120; customers see 100. The error is discovered days later, if ever.
  • Neither user did anything wrong: the system let them act on stale data.

How it's fixed

  • Optimistic concurrency: each save sends the version it was based on (If-Match: "v1"); the server answers 412 Precondition Failed if the record changed.
  • Conflict UI shows who changed what. Changes to different fields merge with one click; the same field asks the user to choose.
  • The user's input is never discarded.
  • (Also good: sending only changed fields with PATCH, and presence indicators like “Bob is editing”.)
Principles: Optimistic concurrency (ETag / version) HTTP 412 + If-Match Conflict resolution UI Never discard user input

4. The ops console where one typo takes down production

Task: take 3 servers out of the staging pool for maintenance. Try it carelessly, the way a tired engineer would during an incident: don't check the environment, and type 30 instead of 3.

(remembers the last environment you used)

✓ GOOD

No environment selected
Environment (choose every time):

What's wrong

  • Mode error: the console silently reopens in the last environment (production), and the two environments look identical.
  • No preview of the effect, and no limits: removing 30 of 32 production servers is accepted instantly.
  • All at once: no batches, no health checks, no abort.
  • This is the shape of real outages (e.g. the 2017 AWS S3 incident: a mistyped input in a capacity-removal command).

How it's fixed

  • No remembered default: choose the environment every time; a big colored banner shows it (red for production).
  • Preview: “remove 30 of 32 → leaves 2 (6%)”.
  • Hard guardrail: never below the minimum healthy capacity (75%). The tool says the maximum you can remove.
  • Type-to-confirm the environment name for production.
  • Staged execution in batches with health checks and an Abort button.
Principles: Visible modes No dangerous defaults Blast radius limits Staged execution + abort Swiss cheese model

Accessibility: Bad vs Good

Four interactive examples of common accessibility barriers and how to fix them. Try each bad version first, then the good one, ideally using only your keyboard (Tab, Shift+Tab, Enter, Space, Esc).

The dark “Screen reader (simulated)” boxes show roughly what a screen reader would announce. It's a simplified model of the accessibility tree, so for the real experience turn on NVDA, VoiceOver or TalkBack. Notes: Accessibility README.

Tip: press Tab once on page load. This page has a skip link, as every page should.

1. The status page you can only read with perfect color vision

Try it: which service is down? Now switch the simulation to Deuteranopia (the most common color-vision deficiency), Grayscale or Blurred vision and ask again. The chips show measured contrast ratios.

Normal text sample (16px)
Large text sample (24px)

What's wrong

  • Status by color only (SC 1.4.1): green/red/orange dots look almost the same with red-green color blindness, in grayscale, or on a dim screen. A screen reader gets nothing at all.
  • Low-contrast text (SC 1.4.3): light gray “Last updated” and the label are far below 4.5:1.
  • Link only distinguished by color: no underline, and barely different from the surrounding text.
  • Error shown only as a pale red border: no text says what's wrong; the border also fails 3:1 (SC 1.4.11).
  • White text on light orange: a brand color that fails contrast badly.

How it's fixed

  • Icon + text + color: “✕ Outage” works in every simulation and for screen readers (the icons are aria-hidden, the words carry the meaning).
  • All text ≥ 4.5:1: same layout, just darker grays.
  • Underlined link: a non-color cue.
  • Error in text, next to the field, tied with aria-describedby and aria-invalid; thick, high-contrast border.
  • Darker variant of the brand orange for the button (keep the light one for large decorative areas).
Principles: Perceivable 1.4.1 Use of color 1.4.3 Contrast (minimum) 1.4.11 Non-text contrast 3.3.1 Error identification

2. The settings page you can't use without a mouse

Try it: click into the panel's top edge, then put the mouse away. Use Tab to reach the toggles, turn off “SMS alerts” with Space, and save with Enter. Watch where the focus goes, and what the simulated screen reader says.

✓ GOOD

  • Email alerts On
  • SMS alerts On
  • Weekly digest Off

Screen reader (simulated)
  • Focus something in this panel…

What's wrong

  • Toggles are plain <div>s with a click handler: Tab skips them entirely. Keyboard, switch and voice-control users can't change any setting (SC 2.1.1).
  • The “Save” div got tabindex="0", so it receives focus, but Enter/Space do nothing, and it's announced as just “Save” with no role.
  • outline: none: when focus lands on “Save” you can't see it (SC 2.4.7).
  • State is color only (light green vs gray), and screen readers get no on/off state.
  • The “Saved” message is faint and not announced.

How it's fixed

  • Real <button>s with role="switch" + aria-checked: focusable, activate with Enter and Space for free, announced as “SMS alerts, switch, on”.
  • Name from the visible label (aria-labelledby), so voice control users can say “click SMS alerts”.
  • Visible :focus-visible ring with strong contrast.
  • State shown three ways: knob position, fill, and “On/Off” text. Also works in Windows high contrast mode.
  • “Settings saved” in a role="status" live region, announced without moving focus.
Principles: Operable Semantic HTML first 2.1.1 Keyboard 2.4.7 Focus visible 4.1.2 Name, role, value 4.1.3 Status messages

3. The product card that makes no sense when read aloud

Try it: press “Read panel” in each screen reader box to hear the card read top to bottom, then “Links list” (screen reader users often jump through links out of context). Then Tab through both cards and click “add to cart”.

✓ GOOD

Wireless headphones

$42.00

★★★★☆ Read 128 reviews

40h battery. Full technical specifications

Screen reader (simulated)
  • Press “Read panel”, or Tab into the card…

What's wrong

  • No alt attribute: many screen readers fall back to reading the file name, “IMG_4027.jpg”.
  • Title is a styled div, not a heading, so users jumping by heading (the most common way to scan a page) never find the product.
  • Stars read character by character: “black star, black star, black star, black star, white star”.
  • Icon-only buttons with no name: announced as just “button”. Which one adds to cart? Even sighted users have to guess.
  • Quantity field has no label (“Qty” is just text next to it).
  • “Click here” / “Read more”: meaningless in the links list.
  • “✓ Added” appears visually but is never announced.

How it's fixed

  • Meaningful alt describing what matters on a product page.
  • Real <h3>, and the card is an <article> labelled by it.
  • Rating as one graphic: role="img" aria-label="Rated 4 out of 5 stars".
  • Wishlist has aria-label and aria-pressed; “Add to cart” has visible text (best option); SVGs are aria-hidden.
  • <label for> on Quantity; 44px targets.
  • Descriptive links: “Read 128 reviews”, “Full technical specifications”.
  • Live region announces “Added to cart. Cart has 1 item.”
Principles: Perceivable / Robust 1.1.1 Non-text content 1.3.1 Info and relationships 2.4.4 Link purpose 2.4.6 Headings and labels 4.1.2 Name, role, value

4. The modal that traps sighted users and loses keyboard users

Try it with the keyboard: Tab to “Delete account”, press Enter. Where is focus now? Press Tab a few times, then try Esc. In the good version, notice that focus returns to the button when the dialog closes.

✓ GOOD

ProfileBillingSecurity

Danger zone

Delete your account?

This permanently deletes your account, 34 projects and all billing history. You can't undo this.
Screen reader (simulated)
  • Focus something in this panel…

What's wrong

  • Focus doesn't move into the dialog. Keyboard and screen reader users are left on the button behind the overlay, and nothing is announced.
  • No focus trap / inert background: Tab walks through links hidden behind the overlay.
  • “Yes”, “No” and “×” are div/spans: a keyboard user can't answer or close the dialog at all.
  • Esc does nothing.
  • Vague text: “Are you sure?” about what? “Yes/No” buttons don't say what they do. Low-contrast “×”.
  • Not exposed as a dialog, so screen readers don't know a dialog is open.

How it's fixed

  • Native <dialog> + showModal(): the browser moves focus in, makes the rest of the page inert, and closes on Esc.
  • Focus starts on the safe action (“Cancel”, via autofocus), so an accidental Enter doesn't delete anything.
  • Focus returns to “Delete account” on close, so users continue from where they were.
  • Labelled and described (aria-labelledby, aria-describedby): announced as “Delete your account?, dialog, This permanently deletes…”.
  • Specific button labels (“Delete account” rather than “Yes”) and a specific consequence (“34 projects”).

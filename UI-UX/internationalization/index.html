Internationalization: Bad vs Good

Four interactive examples of classic i18n bugs and how to fix them. Change the language, locale, currency or time zone in each example's controls and watch both versions react. The good versions use the browser's built-in Intl APIs (backed by Unicode CLDR data).

Notes: Internationalization README.

Examples: 1. Plurals & messages 2. Dates, money & time zones 3. Layout, expansion & RTL 4. Unicode text

1. “You have 22 new message(s)”: plurals and concatenation

Try it: pick Polski and try 2, 5 and 22. Then Русский with 21, العربية with 0 and 2, Français with 0, and 日本語 for the page counter. Also try 1000000.

    ✓ GOOD

      What's wrong

      • n === 1 ? one : plural encodes English plural rules. Polish and Russian need different forms for 2–4, 5+, 22 and 21; Arabic has six forms; French treats 0 as singular.
      • “message(s)” is lazy in English and impossible to translate.
      • Raw numbers: 1000000 instead of the locale's grouping.
      • Concatenated sentence (t('page') + n + t('of') + total) bakes in English word order: in Japanese it becomes nonsense.
      • Arabic text rendered without dir="rtl".

      How it's fixed

      • ICU MessageFormat plurals: translators write as many forms as their language needs; Intl.PluralRules picks the category from CLDR rules.
      • Whole sentences with named placeholders: the Japanese translator puts {total} before {current}.
      • Numbers formatted with Intl.NumberFormat inside the message (#).
      • lang and dir set on the translated content.
      Principles: ICU MessageFormat CLDR plural categories No concatenation Named placeholders Intl.PluralRules / NumberFormat

      2. The order page that's only right in New York

      Try it: switch the locale to Deutsch, 日本語 (imperial era), ไทย and العربية (مصر); the currency to JPY, VND and KWD; the time zone to Kathmandu or Adelaide. Labels stay in English on purpose, so you can focus on formatting.

      ✗ BAD

        ✓ GOOD

        What's wrong

        • Hand-written MM/DD/YYYY: “03/04/2026” means 3 April to most of the world.
        • "$" + amount.toFixed(2): wrong symbol for every non-USD currency, “.00” on yen and dong (which have no minor unit), only 2 decimals for dinar (which has 3), no grouping.
        • Times shown in the server's zone (UTC) with no zone label: the webinar time is wrong for almost everyone.
        • “3 day(s)”, English list commas, kilometers for US users.
        • Ignores calendars (Thai Buddhist year 2569, Japanese era Reiwa 8) and native digits.

        How it's fixed

        • Machine values in, formatting at the edge: the API sends ISO 8601 UTC instants, ISO 4217 codes and minor units; the UI formats with Intl.
        • Intl.DateTimeFormat with the user's locale and IANA time zone, and the zone shown for scheduled events.
        • Intl.NumberFormat with style: 'currency': symbol position, decimals per currency, grouping.
        • RelativeTimeFormat, ListFormat, unit formatting (plus unit conversion for US users).
        • Locale and currency are independent settings: try de-DE with USD.
        Principles: Store machine values, format at display UTC instants + IANA zones ISO 4217 minor units Locale ≠ currency ≠ time zone CLDR

        3. The settings screen designed for English only

        Try it: switch to Deutsch (long words), العربية (right-to-left), Tiếng Việt (stacked diacritics), 日本語 (different word order), and Pseudo-localized, the developer's test language. In pseudo mode, any text without [brackets] is hardcoded, and several bracketed pieces in one sentence reveal concatenation.

        ✗ BAD

        ✓ GOOD

        What's wrong

        • Fixed-width tabs and buttons sized for English: “Einstellungen” and “Änderungen speichern” are cut off.
        • Fixed-height heading with line-height: 1: Vietnamese marks (“Cài đặt tài khoản”) get clipped.
        • Physical CSS (text-align: left, left: .55rem, right: 0): with dir="rtl" the text, icon and badge end up on the wrong sides, and the “Next” arrow points backwards.
        • “C++ Primer (5th ed.)” not isolated, so the bidi algorithm scrambles its punctuation inside Arabic text.
        • Concatenated sentence: German and Japanese verbs end up in the wrong place.
        • “Cancel” is hardcoded: it never gets translated (pseudo mode shows it without brackets).

        How it's fixed

        • Content-sized, wrapping layout (flexbox with flex-wrap, padding instead of widths).
        • Generous line height and no fixed heights on text.
        • lang + dir attributes and CSS logical properties (text-align: start, inset-inline-start, padding-inline), so the whole layout mirrors automatically.
        • Directional icons mirrored in RTL ([dir=rtl] .flip { transform: scaleX(-1) }).
        • <bdi> around user names and product titles.
        • One message per sentence with placeholders, and every string from the catalog.
        Principles: Text expansion Pseudo-localization RTL mirroring CSS logical properties Bidi isolation (<bdi>) lang attribute

        4. Names, search, sorting and emoji: Unicode text handling

        Try it: type your own name, search for nguyen or José, switch the sort order to Svenska or Tiếng Việt, and change the preview limit. One contact was saved in decomposed Unicode (NFD), as happens with text from some keyboards, file systems and copy-paste sources.

                    What's wrong

                    • /^[A-Za-z ]+$/ name validation rejects Nguyễn, O'Brien, José, 李小龙, محمد: most people on Earth.
                    • toLowerCase().includes() search: “nguyen” doesn't find “Nguyễn”, and even typing “José” exactly fails because the stored copy is NFD.
                    • array.sort() sorts by code unit: uppercase before lowercase, accented letters after “z”, regardless of language.
                    • .length and .slice() count UTF-16 code units: the counter is wrong and truncation can cut an emoji in half (�).
                    • Not shown but related: Enter-to-send while an IME is composing (Japanese/Chinese input) sends half-typed messages. Check event.isComposing.

                    How it's fixed

                    • Permissive validation: non-empty, ≤ 100 graphemes, no control characters (\p{Cc}).
                    • Normalize + fold for search: NFD, strip combining marks, map đ→d, ø→o (they don't decompose), lower-case. In production: search-engine ICU/ASCII-folding analyzers.
                    • Intl.Collator(locale): Swedish puts Å Ä Ö after Z; Vietnamese puts Đ after D.
                    • Intl.Segmenter counts and cuts by grapheme (what people see as one character), and shows code units and UTF-8 bytes for DB limits.
                    Principles: Unicode normalization (NFC/NFD) Grapheme clusters Locale-aware collation Accent-insensitive search Falsehoods about names
                    Companion to the Internationalization README. Output depends on your browser's CLDR/ICU version, so details may differ slightly between browsers.

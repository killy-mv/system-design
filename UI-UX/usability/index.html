Usability: Bad vs Good

Three interactive examples of common usability mistakes and how to fix them. Try the bad version first, then the good one. Notes: Usability README.

Examples: 1. Sign-up form 2. Payment button 3. Deleting a file

1. The sign-up form that punishes mistakes

Try it: fill in both forms with a short password (e.g. abc) and an email without “@”, then submit.

✗ BAD
✓ GOOD
Enter an email address like name@example.com.

At least 8 characters.

Any format — e.g. 090 123 4567 or +84 90 123 4567.

What's wrong

  • Placeholders used as labels: they disappear as soon as you type, so you can't check what a field was for.
  • Unexplained rules: you only learn the password rules after breaking them.
  • Vague error (“Invalid input.”) in tiny text at the top, far from where you're looking (change blindness).
  • The form clears itself on error, so you lose everything you typed.
  • Strict format: the phone field rejects spaces, dashes and “+”.
  • Pale, low-contrast button that says “Submit”, which doesn't tell you what happens next.

How it's fixed

  • Labels that stay visible above each field, with <label for> for screen readers.
  • Rules shown up front as hints (“At least 8 characters”), and optional fields are marked.
  • Inline validation on blur: each error appears next to its field and says how to fix it.
  • Your input is kept, and focus moves to the first field with a problem.
  • Accepts any phone format and normalizes it (Postel's Law).
  • Correct input types and autocomplete for the right mobile keyboard and autofill; the button says “Create account”.
Principles: Recognition over recall Error prevention Help users recover from errors Visibility of system status Postel's Law Gestalt: proximity

2. The “did it work?” payment button

Try it: click “Pay” once, and if nothing seems to happen, click again (most real users do). Watch the bank statement.

✗ BAD
Wireless headphones$42.00
Total$42.00
// Your bank statement
✓ GOOD
Wireless headphones$42.00
Total$42.00
// Your bank statement

What's wrong

  • No feedback: for ~2.5 s nothing changes, which is well past the 1-second limit for keeping the user's flow.
  • Users assume the click didn't register and click again, and every click creates a new charge.
  • The backend isn't idempotent, so it can't tell a retry from a new purchase.
  • The final message (“Done”) doesn't say what happened or how much was charged.

How it's fixed

  • Instant feedback (<100 ms): the button switches to “Processing…” with a spinner.
  • Button disabled while the request is in flight.
  • Idempotency key: one key is generated per checkout and the server dedupes on it, so even a retry from a flaky network can't charge twice. (The disabled button alone isn't enough; it only guards this one tab.)
  • Specific confirmation: “Paid $42.00. Order #A-1042 confirmed”, and the button label says the amount up front.
  • Status announced to screen readers via aria-live.
Principles: Visibility of system status Feedback (Norman) Gulf of evaluation Response time limits (0.1 s / 1 s / 10 s) Idempotent APIs

3. The tiny delete icon with a confusing confirmation

Try it: in the bad version, quickly edit “Q3-report.pdf” by clicking the first icon, the same spot as on the other rows, then read the dialog carefully. In the good version, delete a file and then change your mind.

✗ BAD

    Warning
    Are you sure you don't want to cancel this operation?

    ✓ GOOD
      Deleted files stay in Trash for 30 days.

      What's wrong

      • Tiny targets placed side by side: ✎ (edit) and 🗑 (delete) are a few pixels apart, so a slip is easy (Fitts's Law, touch-target size). Here the icons are even swapped on one row.
      • Unlabeled icons: you have to guess what they mean.
      • Double-negative dialog: “Are you sure you don't want to cancel…?” Which button deletes?
      • Generic buttons: “OK” / “Cancel” don't say what will happen, and the dangerous action is the highlighted default.
      • No way back: the hard delete is permanent and there's no undo.

      How it's fixed

      • Labeled buttons (“Rename”, “Delete”) with large targets and a gap between them; the order is the same on every row.
      • Undo instead of confirm: deleting is immediate, and a toast offers “Undo” for a few seconds. That's faster, and it doesn't train users to click OK without reading.
      • Soft delete: files go to the Trash for 30 days, so the backend can restore them.
      • Keep confirmation dialogs for truly irreversible actions, and make them specific: “Delete project ‘Apollo’ and its 312 files?” with buttons “Delete project” / “Keep project”.
      Principles: User control and freedom (undo) Error prevention (slips) Fitts's Law Consistency Match the real world (plain language) Soft delete

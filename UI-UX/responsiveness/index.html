Responsiveness: Bad vs Good

Four interactive examples of UIs that feel slow or broken, and how to fix them. In every example both sides talk to the same simulated server with the same latency. The only difference is the UI design. The dark boxes show the simulated network traffic.

Notes: Responsiveness README.

Examples: 1. Optimistic UI 2. Loading & layout shift 3. Search & frozen input 4. Long operations

1. The to-do list that waits for the server

Try it: add three tasks quickly and tick one off, in both lists. Then turn on “Server fails” and add another task.

✗ BAD

    // network

    ✓ GOOD

      // network

      What's wrong

      • Nothing happens on click until the server answers. No pressed state, no pending item, so users click again and get duplicate tasks.
      • The checkbox refuses to tick until the round trip finishes; it feels broken.
      • The input stays full, so you can't type the next task until the first one is saved.
      • On failure your text is thrown away and a tiny “Error” appears far from where you were looking.

      How it's fixed

      • Optimistic update: the task appears instantly (marked “Saving…”) and the input clears and keeps focus, so you can add the next one straight away.
      • Checkbox ticks instantly; it rolls back with a message if the server rejects it.
      • Failed tasks are kept and marked “Not saved” with Retry and Remove. Nothing the user wrote is lost.
      • Client-generated ID used as an idempotency key: retries can't create duplicates on the server.
      • Failures announced in a role="status" live region.
      Principles: Optimistic UI Feedback < 100 ms Visible rollback Idempotency keys Client-generated IDs

      2. The feed that loads blank, then jumps under your finger

      Try it: press “Load feed” on both sides, and as soon as posts appear, try to click “Read” on the first post. Then press it again (a reload). Server timing for both sides: feed data 1.5 s, images and ad 2.3 s.

      ✗ BAD

      Layout shift: press “Load feed”.
      // network

      ✓ GOOD

      Layout shift: press “Load feed”.
      // network

      What's wrong

      • Blank area + spinner for the whole wait: nothing to look at and no idea what's coming.
      • Images have no reserved space, so when they load, every post jumps down.
      • An ad is injected at the top after content appeared, pushing everything down. Aim for “Read” and you hit “Shop now”.
      • Reload throws away what you already had and shows the blank spinner again.

      How it's fixed

      • Skeleton screen instantly, with exactly the same dimensions as the real posts.
      • Progressive rendering: text appears as soon as it arrives (1.5 s), images fill reserved boxes later.
      • Ad slot reserved from the start, so nothing moves: measured shift is 0 px.
      • Stale-while-revalidate: reload shows cached posts immediately with a small “Updating…” note.
      • aria-busy while loading and a polite “Feed loaded” announcement.
      Principles: Skeleton screens Progressive rendering CLS: reserve space Stale-while-revalidate Occupied waits feel shorter

      3. The search box that freezes and shows the wrong results

      Try it: type pineapple quickly in both boxes. Watch how fast your letters appear, the request count, and which query the final results are actually for. The simulated server is slower for shorter queries (they match more items), which is realistic.

      ✗ BAD

      Keystroke → screen: type to measure.
        // network · requests sent: 0

        ✓ GOOD

        Keystroke → screen: type to measure.
          // network · requests sent: 0

          What's wrong

          • Heavy synchronous work on every keystroke (~150 ms here, like re-filtering and re-rendering a huge list) blocks the main thread, so your letters appear late (poor INP).
          • A request per keystroke: 9 requests for “pineapple”, wasting server capacity.
          • Out-of-order responses: the slow request for “p” comes back last and overwrites the correct results, so the list doesn't match what you typed.
          • No sign that a search is in progress.

          How it's fixed

          • Input handler does almost nothing, so letters appear instantly. Heavy work belongs on the server or in a Web Worker.
          • Debounce (250 ms): search runs once you pause; usually 1–2 requests instead of 9.
          • AbortController + request IDs: superseded requests are cancelled and late responses ignored, so results always match the input.
          • Old results stay visible but dimmed with a “Searching…” note instead of flashing empty.
          • Result count announced politely to screen readers.
          Principles: Keep the main thread free INP ≤ 200 ms Debounce the work, not the input Cancel stale requests Keep stale content while refreshing

          4. The export that holds you hostage

          Try it: start an export on both sides (it takes about 7 seconds on the server), then try to type a note while you wait. In the good version, also try “Cancel”.

          ✗ BAD

          Please wait…
          // network

          ✓ GOOD

          Q3 sales report is readyDownload
          // network

          What's wrong

          • A blocking overlay freezes the whole UI for the full duration, so you can't type your notes or do anything else.
          • Indeterminate “Please wait…” for 7 s: no idea whether it's 10% or 90% done, or stuck.
          • No cancel. Clicked by mistake? Too bad.
          • One long HTTP request: if the tab closes or the connection drops, the work is lost (and long requests hit gateway timeouts at scale).

          How it's fixed

          • Async job: POST /exports returns 202 Accepted + a job ID immediately; a worker does the work.
          • Determinate progress with steps (“Building PDF · 54% · about 3 s left”) from a progress endpoint.
          • The rest of the UI stays usable, so you keep typing your notes.
          • Cancel at any time.
          • Notification on completion (toast + live region); in a real app the job also survives a page refresh and can email a link.
          Principles: Async job pattern (202 + polling/SSE) Determinate progress Uncertain waits feel longer User control and freedom Notify on completion
